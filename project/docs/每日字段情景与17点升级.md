# 每日字段情景与 17 点升级

每日巡检按**任务所处情景**提问，不是把每一列都变成必填。10:00 对最新项目数据提出具体问题；17:00 将尚需处理的问题、真实回复情况和延期/资源风险汇总给已配置的项目负责人。两次触发采用项目时区及已核验工作日，属于本项目约定，并非管理学统一规定。

本版增加 WBS 叶子任务的条件问题，以及持久化的发送、回复与读取覆盖证据。运维、资源、决定等沿用既有巡检与群行动；不能把下面的 WBS 检查宣称为所有表、每个字段都有同等规则。任务就绪、资源关系和逐级影响见 [每日任务巡检与资源影响](每日任务巡检与资源影响.md)。

## 18 类情景与问法

“新增”表示已有可执行的 WBS 条件问题；“既有”表示复用原校验、风险或执行台账；“建议”需要补充数据或宿主规则后才能自动判定。只在触发条件成立时追问，不从空值猜测成员行为。

| 情景 / 当前覆盖 | 何时问、向谁问 | 要补的事实与解除条件 |
|---|---|---|
| 1. 范围、责任、优先级不清 · 新增 | 未关闭叶子缺说明、完成标准、有效负责人/验收人；缺优先级或 P0 缺依据。负责人补充，无可达负责人由 PM 协调 | 交付什么、由谁承接、如何验收、为何紧急；补齐实际缺项及有效责任关联 |
| 2. 缺开始计划 · 新增 | 「当前预计开始」空，向负责人问开工约束 | 最早何时可开始、缺什么输入；补当前计划及依据，不能填虚构实际日期 |
| 3. 缺完成预测 · 新增 | 「当前预计完成」空，向负责人问难点、剩余工作量、不确定性 | 是否需拆成可验收子任务、验证未知量、更多资源/时间；提出预计完成及依据。不能自动拆任务、延长承诺 |
| 4. 到开始日但实际开始空 · 新增 | 当前预计开始已到，或状态进行中/受阻/待确认却无实际开始 | 已开工漏填还是尚未开始？前者补真实日期，后者说明原因、预计开工及交付风险。空值本身不证明没开工 |
| 5. 日期与状态矛盾 · 新增＋既有校验 | 已填实际开始却仍待开始/待分流；实际完成却未关闭；计划起止倒置 | 核对哪个事实有误、来源是什么；未来实际日期、实际起止倒置由数据校验处理。受控修正，不自动补今天或改历史 |
| 6. 完成节点已到却无实际完成 · 新增 | 优先对照原计划完成，缺原计划才用当前预测；当天到期与日期已过分开 | 已做完漏填、尚未完成还是待验收？给成果/剩余量、当前预测及风险原因。当天上午不提前宣布已延期 |
| 7. 报完成但事实不齐 · 新增 | 已确认完成仍缺实际开始、实际完成或完成依据 | 核对真实完成事实及证据；这是一项完成记录核查，不向正常已完成任务继续催日常进度 |
| 8. 承接/进展过期或泛泛回复 · 新增＋回复证据 | 无当前负责人本人反馈，或到已配置更新间隔。收到、处理中不等于已回答问题 | 是否收到并能承接；上次后完成什么、剩什么、困难与下一步。具名业务反馈与群回复分别保存 |
| 9. 预测偏离承诺或反复改期 · 既有 | 当前预测、原计划、周确认承诺及真实历史不一致 | 说明变化、原因、影响和补救。没有历史不能声称反复改期；疑似规避延期的日期修改仍私下交 PM 核实 |
| 10. 受阻/等待无恢复安排 · 新增 | 明确受阻，或等待条件缺有效下一检查点/检查点已到 | 卡在什么条件、谁解除、能否部分继续；继续还是等待、恢复条件/预计时间，未知时给下次核对时间 |
| 11. 延期补救不全或到期未验证 · 新增＋既有 | 已有延期/风险，缺原因、影响、措施、落实人、预计补救日；措施到期缺实际结果 | 原因→措施→负责人→预计落实→实际落实及验证；补救日不替代任务基线，写了措施不等于已解决 |
| 12. 任务过大/在制时间异常 · 拆分问法已实现；自动年龄阈值为建议 | 无完成预测时已问难度/拆分；额外年龄阈值需要真实开始、历史分布和项目政策 | 用可验证子成果、减少并行或专业支持；不能把统一“三天”当行业标准，SLE 也不是单项承诺 |
| 13. 前置/接口/外部输入缺口 · 既有 | 显式依赖、未就绪接口及需用日期证据；两端负责人协调 | 输入规格、最晚需用、交付承诺、替代/换序；接口关联开发任务不代表必须在开发开始前就绪 |
| 14. 人力/物资/环境未落实 · 既有 | 已登记休假重叠、容量不足、物资/账号/环境未到位或关键事实未知 | 替补、最晚到位、关联任务及依据。未知容量与已确认短缺分开；远程/兼项不直接等于能力不足 |
| 15. 决定未形成或无有权人 · 既有 | 开放决定缺结论/决定人/时间，或最迟处理日已到 | 请明确有权人、选项/取舍、决定期限与依据；建议不冒充批准，越权事项请求 PM 支持 |
| 16. 待验收排队/返工 · 新增＋既有 | 待确认、实际完成与未关闭状态需核对，找登记验收人 | 材料、评审安排及结论；返工继续沿已登记执行任务跟踪。无返工事实不自动创建返工任务 |
| 17. 交接、责任人或回复关联变化 · 既有＋回复证据 | 负责人已换、旧回复人不同、回复没有对应行动/问题 | 保留原发送对象和交接证据；旧负责人的回复不替新负责人承诺，也不把旧截止归责给刚接手的人 |
| 18. 子项阻碍与父级/全局冲突 · 既有 | 未结叶子影响父级交付、父级报完成但子项未完，或明确依赖传播 | 给出来源→叶子→父级→项目路径；无关键路径/浮时/工时依据，整体延期天数写待评估 |

上述矩阵是结合用户要求和专业方法作出的项目设计。进度事实、剩余工作及截止一致性依据 [GAO Schedule Assessment Guide，Best Practice 9](https://www.gao.gov/assets/gao-16-89g.pdf)；每日检查、难度讨论与可验证拆分参考 [Scrum Guide 2020](https://scrumguides.org/scrum-guide.html)；工作年龄、在制数量和主动解阻参考 [Kanban Guide 2025.5](https://kanbanguides.org/the-kanban-guide/2025.5/)。这些方法支持条件判断，不要求填写未来实际日期，也不授权 agent 自动延期。

升级聚焦需要管理支持的例外：跨团队资源、权限范围或交付取舍，并写清需要什么决定。依据为 PMI 的实践文章 [Escalate Decisions to Project Sponsors](https://www.pmi.org/learning/library/2019/04/07/16/05/escalate-decisions-project-sponsors-11152) 和 [Escalate Is Not a Dirty Word](https://www.pmi.org/learning/library/escalate-not-dirty-word-3637)。它们不是 17:00 时限的规范性来源，也不支持因未回复推断工作态度。

## 字段如何落地

用户说的“计划开始/完成”，本包日常更新对应「当前预计开始/完成」；「原计划开始/完成」是单独保留的基线。实际起止只记录真实事件。未开工、未完成的未来任务可以没有实际日期；取消任务、已验证完成任务不承担普通进度催填。只读/公式、可选且不适用的字段无需为了消除空白而填写。

延期/风险涉及「实际延期说明/延期风险说明」「延期影响」「延期补救措施」「补救责任人」「预期补救时间」「实际补救时间」「补救验证结果」。继续推进或等待的事实写入已有进展、「等待事项/前置输入」「下一步动作」「下一步最迟时间」；恢复日不知道时给条件及复核时点，**下一步最迟时间不自动等于恢复日**。是否修改基线、批准资源或验收通过由有权人决定。

上午问题包含稳定问题 ID，便于分别关联回复。`required_fields` 是业务字段；`response_fields` 是本次要求回答的问题 ID，二者不是同一组列。一个问题已回答，不代表其他问题或任务已经关闭。

## 10 点提问，17 点回看

1. 10:00 读取最新事实，按情景和真实责任人组织问题，成功发送后固定保存发送时点、收件人、群、消息 ID、行动 `occurrence_key` 和问题 ID。
2. `response_cutoff` 默认 17:00，标为 **本次回复截止**，与任务完成/行动执行/补救 DDL 分开。发送晚于截止的新问题不立即算逾期；默认至少有 `min_response_minutes: 30` 分钟回应机会。
3. 白天由已绑定的原生工具或受控宿主读取群消息，核验发送人身份、项目/群、来源消息和时间。按问题保存答复；字段更新可以解除资料问题，但不是群回复证据。回复文字也不会自动写入业务日期或批准决定。
4. 17:00 再读业务数据与真实回复。已解除的问题停止；已回复但仍有延期/资源风险继续进入风险摘要。新出现或尚未成功询问的问题另列，不归入成员未回复。
5. 汇总给 `escalation_recipient_id` 指定成员；未指定时用项目 PM。必须有有效、可达、在范围内的真实身份。作者邮箱不是接收者身份，无法识别时列待配置，不猜 @ 对象。

| 证据情况 | 下午的表述 |
|---|---|
| 成功发送且读取覆盖完整，无对应回复 | 截至回复截止未观察到回复；附成功消息与覆盖依据 |
| 成功发送但没有完整读取覆盖 | 回复情况待核验；不能说成员没回复 |
| 仅回复“收到” | 已回应、所问事实待补；不计为未回复，也不自动关闭问题 |
| 只回答一部分 / 全部问题 | 已部分回答 / 已回答；列仍缺的问题与尚未解除的业务风险 |
| 正常答复但延期仍存在 | 已回复、风险未解除；继续请求补救落实或管理支持 |
| 字段已补齐、对应问题已解除 | 停止该项追问；无群证据时仍不声称在群里回复过 |
| 发送失败、结果未知、无可达对象、从未发送 | 提醒失败 / 送达待核验 / 待配置 / 未询问；与未回复分开 |
| 17:00 新问题、未到回复截止或回应窗口太短 | 新问题 / 尚未到期 / 回应时间不足；可汇报已知风险，不追责未答 |
| 当前负责人已变 | 列交接变化，旧发送仅代表当时向原负责人询问；需重新关联责任与跟进 |

一次发送成功只证明通道成功，不证明人已阅读。`unanswered` 要求完整覆盖从成功发送时点到回复截止；部分读取、缺页、工具无权限不能证明没有回复。一个消息回答多个任务时分别关联相应行动和问题；不能用“一句收到”批量清掉所有行动。

实际发送时点在成功返回后采集，不使用读取项目或开始这一轮巡检的时间；读取慢、消息分批较多时，也不能虚增成员的回应机会。任务或资源已收到答复、资料已补齐，仍不代表延期风险解除；同一记录的不同资源缺口分别保留。

## 群消息示例

以下为虚构正文，实际 @ 由工具使用核验后的飞书身份生成，日期只作格式示意。

```text
@任务负责人｜任务 WBS-DEMO-7：接口联调
【补填 / 确认】当前预计开始已到，实际开始为空。
1. 已开工漏填，还是尚未开始？已开工请补真实开始日。
2. 未开始的话，原因、预计开工日、对完成日的风险是什么？
本次回复截止：2026-11-13 17:00（Asia/Shanghai）
执行 DDL：待确认；任务预计完成：11月16日（不是回复截止）。
回填：实际开始或当前预测、进展及风险/补救依据。
影响：接口联调 → 接口验收 → 项目交付；总工期影响待评估。
```

```text
@项目负责人｜17点项目跟进
需支持：接口替代方案须由你决定，最迟决定时间待确认。
风险：WBS-DEMO-7 接口未就绪，影响接口验收；总工期影响待评估。
跟进：10:02成功询问；负责人10:40已部分回答，仍缺预计恢复及补救完成日。
当前措施：能继续做校验；正式联调等待接口权限，下一核对时间16:00已过。
另有1项截至17:00未观察到回复（已完整核验群消息），1项回复情况待核验。
提醒执行异常另列：1项未送达；不计入成员未回复。
```

实际汇总保留消息/记录来源、责任人与当前计划和补救日期，按大小限制分段、持久防重。首次真正发送冻结截至时点与分段；成功/未知段不重复发送，失败段恢复时仍保留该次时点，不冒充重新采集的报告。后续变化不重发已发送的整份日报，空汇总不占当天记录。HTML 继续展示紧凑摘要与折叠证据，不追加整份情景长表。日期篡改疑点延续私下 PM 核验渠道，不混入公开群汇报。

## 宿主接入和证据导入

需要宿主在项目时区 10:00、17:00 唤醒 `agent-tick`，并提供真实群消息读取/事件、身份映射及完整性依据；配置时刻不等于已经安装定时任务。未知年度、非工作日、项目暂停/结项、有效期外或静默期仍不自动发送。离线 Excel 可预览问题和风险，不能建立真实群回复事实或发送 @。

CLI 在飞书模式下会传入真实发送时钟；原生宿主若直接调用 `dispatch_tick`，须提供可信的 `delivery_clock`。固定 `now` 只适合离线演示/确定性测试。`response_cutoff` 和 `escalation_time` 使用项目本地 `HH:MM` 格式。

受控宿主可调用 `followup-evidence-import`，先校验预览，再写入同一持久执行台账。配置 `reply_evidence_sources` 仅允许实际受信任的来源 ID；空列表默认不接受任何来源。**白名单和 JSON 内容本身不是身份认证**：宿主必须核验原始消息、真实发送人和读取分页，转换为已映射的内部人员 `id`，再调用导入。

```powershell
python -m pm_core.cli followup-evidence-import --config work/agent.json --ledger work/runtime.sqlite3 --file work/replies.json
python -m pm_core.cli followup-evidence-import --config work/agent.json --ledger work/runtime.sqlite3 --file work/replies.json --apply
```

导入使用已有台账中的成功发送记录；不要新建空台账来补历史。飞书模式使用真实时钟，不能通过 `--now` 捏造时间；Excel 的演示时钟仅用于本地样例。以下是假数据结构示意，不能直接应用到真实项目：

```json
{
  "source_id": "configured-host-source",
  "project_id": "PROJECT-DEMO",
  "chat_id": "configured-project-chat",
  "replies": [{
    "occurrence_key": "key-from-successful-action",
    "prompt_message_id": "successful-prompt-message-id",
    "message_id": "actual-reply-message-id",
    "sender_id": "internal-person-id-mapped-from-real-sender",
    "at": "2026-11-13T14:00:00+08:00",
    "quote": "实际回复的相关原文",
    "kind": "answer",
    "answers": {"start_unconfirmed:started": "已开始，正在补录实际日期"}
  }],
  "coverage": [{
    "id": "unique-read-observation-id",
    "from": "2026-11-13T10:00:00+08:00",
    "through": "2026-11-13T17:00:00+08:00",
    "captured_at": "2026-11-13T17:01:00+08:00",
    "complete": true,
    "evidence": "实际工具读取来源、页数和完整覆盖依据"
  }]
}
```

`kind: "ack"` 只表达回应，不能带回答；`answer` 的键必须是该次成功发送的真实问题 ID，且内容非空。相同回复涉及多个行动时分别提交各自 `occurrence_key`。正向回复可以独立成立；只有要断言“未观察到回复”时才需要完整窗口覆盖。项目/群/身份/时间/问题关联不符的证据不得用来压下升级。

配置、真实接入及发送结果恢复见 [飞书接入](../references/feishu-setup.md) 和 [执行台账恢复](每日任务巡检与资源影响.md#发送结果未知时怎样恢复)。本次交付没有安装真实 10:00 / 17:00 唤醒，也没有向项目群发消息。
