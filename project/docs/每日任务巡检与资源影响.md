# 每日任务巡检与资源影响

每个项目工作日 **10:00（项目时区）**，智能体从同一份最新数据检查项目全局、父级任务和最小子任务，同时核对人力、接口、决策、物资等资源是否落实。报告中的“每日巡检与逐级影响”和“延期风险与资源落实”供日常跟进及周五审议复用。

## 怎样算具备执行条件

可以先收录一条不完整的待分流任务，但资料未完善时不能把它当作已经编排好的执行任务。每个未关闭叶子任务检查以下内容：

| 检查 | 填什么 / 谁补 |
|---|---|
| 工作说清楚 | 标题、工作说明、可验证完成标准；任务负责人补充，PM 核对归属 |
| 找得到负责人 | 负责人关联到有效通讯录记录，有可用联系身份；未指定或失效交 PM 协调，不向未知对象发送 |
| 计划已编排 | 当前预计开始、预计完成且日期有序；原基线另行保留，不用改基线消除延期 |
| 验收责任清楚 | 指定验收人、明确完成标准；验收与子任务完成数分别看 |
| 有本人反馈 | 近期进展、进展确认时间、进展确认人为当前负责人；自动化不伪造本人反馈 |

投影会区分“资料待补”“承接反馈待确认”“可执行 / 跟进中”，不会自行修改原任务状态。存在负责人或状态为“进行中”不能证明成员已收到派单。现有反馈字段只能说明已登记当前负责人本人反馈，**不是正式签收、身份认证或最新一次派单的承接证明**；有重新派单争议时回查原始会议/消息依据。

未来已排期工作仍核对基本资料；尚未到开工日不会因缺少今日进展被催成“已经停工”。执行中的任务按进展确认时间检查信息是否陈旧，不用任意字段修改时间代替业务反馈。无计划、无负责人、无明细的待分流任务也会进入待补清单，不因日期为空而漏掉。

## 上午 10 点怎么运行

1. 宿主在项目时区 10:00 唤醒，运行 `agent-tick` 或遵守同等规则的原生工具流程。新参数为 `workflow_time: "10:00"`；保留原有 09:00 人力/周会收集，以及既定异常巡检。
2. 先核对项目有效期、项目状态和已核验工作日，包含调休上班日。未知年度、非工作日、暂停/结项或有效期之外不自动催办。
3. 10:00 前不发本轮巡检；宿主延迟时可在当日之后补执行。由持久执行台账防重，结果未知先核验，不因重试而重复发送。
4. 按人合并缺口，说明具体任务、需维护字段及影响；未分配/不可联系任务交有效 PM，连 PM 也不可达则保留待配置结果。
5. 每次发送前重读事实，已补齐、关闭、取消的对应事项停止催办；不把“未反馈”解释为“没工作”。

任务当前预计完成日只用于交付计划对照，不是资料补填期限；未另行约定补填时点时，提醒明确交由 PM 确认，不能把交付日期当作填写截止。

这是 Skill 的执行规则与程序入口，**不是已在飞书租户安装的定时任务**。宿主需要绑定真实工具、凭据、白名单、持久台账和唤醒能力；默认配置不发送消息。Excel 模式输出待维护清单，不能靠 Excel 自己 @ 成员。

## 群里逐项跟进，HTML 按需追溯

日常待办由智能体在已配置的飞书项目群按责任人合并，真实 @ 对应成员，每项分别列明“决策 / 执行 / 补填 / 协调”、具体动作、DDL、完成或回填依据、来源和简短影响。不要把完整风险报告直接粘贴进群，也不要只发“请更新进度”。HTML 默认保留简明风险卡，证据、完整逐级链与口径在详情中展开；飞书汇报文档仍可保留完整证据。

| 事项 | 跟进对象 |
|---|---|
| 需要决定取舍、批准或结论 | 来源记录明确的决定人；记录有负责人不等于该人有决定权 |
| 接口、物资、任务执行及结果回填 | 已登记执行负责人 |
| 人力安排、容量、休假影响及替补协调 | PM 汇总协调；例行人力确认仍只面向非员工 |
| 责任缺失、身份失效或无法联系 | 有效且可达的 PM 协调指定；PM 也不可达则保留待配置结果 |

员工仅免例行人力确认，**员工承担的执行、补填、验收和决定事项照常跟进**。消息必须使用已核验且在通知范围内的真实飞书身份；姓名或来源内容中出现 `@` 不会变成有效提醒，也不能扩大通知到全群。

每项 DDL 来自该行动已有的真实期限，并说明依据。尚未约定的期限写“待确认”，同时请责任人补充承诺；任务预计完成日、接口预计就绪日、休假窗口和周容量起点另作事实展示，不能用来替代补填/答复期限。需要取舍的建议不等于已获批准。

预览与实际发送使用同一结构化内容。合并同一义务的重复提醒，保留不同任务、动作及期限含义；长清单按人分段，每段分别记录发送结果。发送前重读最新事实，资料已补齐、事项已关闭或决定已落实后停止对应提醒；其他未解决事项继续保留。发送成功、结果未知及部分分段失败分别处理，不能为了补发一段而重发所有已成功段落。

桥接默认每段最多 5 项、3500 字符，可配置 `group_max_items`（1–10）和 `group_max_chars`（1200–6000）。较长内容保留摘要及来源提示，完整行动结构留在预览中；过长来源 URL 不伪造截断链接。真实 @ 由消息工具按接收人的飞书身份生成，下面是正文格式的**虚构示例**，不是已发送消息：

```text
项目待办｜请按编号逐项处理；未约定DDL的事项请确认期限。
1.【决策】确认接口认证方式
事项：确认采用方案并记录决定结论。
DDL：2026-11-13T10:00:00+08:00；依据：登记事项的最迟处理时间
完成/回复：回填决定结论、决定人、决定时间及依据。
来源：提醒与风险/REG-DEMO-1 https://example.invalid/decision/1
影响：接口联调的前置结论待落实。

2.【执行】恢复接口联调
事项：排查联调失败并回填处理结果。
DDL：待确认；依据：尚未登记本行动处理期限，请确认具体日期/时间
完成/回复：回填处理结果、验证依据及下一步。
来源：WBS总表/WBS-DEMO-2 https://example.invalid/task/2
影响：影响上级接口验收准备。
任务当前预计完成日：2026-11-16（非本次回复DDL）
```

同一成员同时承担两个角色时可以收到上面这样的合并消息；不同责任人的事项分别组织，不能用一条 @ 将他人的责任移给被提及的人。批准变更、验收和决定的实际回填仍遵守具名来源与权限契约，群催办本身不授予批准权限。

已记录“批准状态 + 决定结论 + 决定人 + 不晚于数据时点的决定时间”后停止该决策请求，不要求重复作决定。这仅完成决策环节；后续落实要关联已有 WBS、运维或登记事项的执行记录继续跟进，不能从决定文字凭空合成新的执行义务。已登记的补救措施可单独推进，不必等到补救期限逾期才催办。

### 发送结果未知时怎样恢复

群提醒有两层持久记录：每段消息的 `batch_key` 和该段每项行动的 `occurrence_key`。`runtime-reconcile` 每次只核验一个键，不自动连带修改另一层。只恢复批次、遗漏行动记录时，未知行动仍会停止发送，这是防重保护。

1. 暂停该项目的宿主 tick，在群历史中核查这一段是否实际送达，保存消息链接、查询结果及核验时点；只处理实际核验过的段落。
2. 从对应发送结果的 `detail.batch_key` 和 `detail.items[].occurrence_key` 取得两层键；宿主须持久保存结果，丢失时先查原执行台账，不重建一套新台账。
3. 先对该 `batch_key`，再对它所属的每个 `occurrence_key`，逐个提交同一事实结论及真实依据。确认已送达用 `applied`，确认未送达才用 `not_applied`；未确认不恢复。每个键准备一份 JSON，例如 `{"key":"实际台账键","outcome":"not_applied","evidence":"本段未送达的实际查询依据"}`，运行 `python -m pm_core.cli runtime-reconcile --ledger work/runtime.sqlite3 --file reconcile.json --apply`。路径换成该项目实际持久台账。
4. 两层核验齐全后恢复 tick；程序仍会重读业务事实，已解决事项不再发送。未送达且仍待办的行动才可重试，其他成功或未知段落保持原状态。不得通过清空台账、更换批次大小或伪造核验依据绕过防重/重试次数。

## 由最小子任务看向全局

材料同时显示全项目有效叶子完成数、父级去重汇总、每条叶子的资料与本人反馈及逐级路径。未就绪任务仍在项目未结分母中，不能为了“进入流程”把它们从进度表隐藏。

- **父子层级**：叶子任务 → 实际父级 WBS → 项目。子任务未完成是父级尚不能完成的依据；父级已报完成但子项未完时列出一致性缺口，不自动改状态。
- **执行依赖**：明确登记的前置 → 后继另列为潜在传导，不把“父子关系”和“前后置关系”混为一谈。
- **交付与日期**：列出关联交付物、验收结果与有据的日期越界。缺工期、浮时、任务工时等关键依据时标记“项目交付日期影响待评估”，不自动宣称项目必延期几天。

一个资源问题关联多个任务时逐条列出路径，受影响任务去重；风险记录数与受影响叶子数是两种读数，不能相加。叶子完成比例也不等于工时加权项目完成率。

## 未落实资源统一进入延期风险

| 资源 | 登记位置与依据 | 如何评估 |
|---|---|---|
| 人员容量 / 兼项 | 人员周资源安排、每日工作安排、任务负责人/成员/有效参与关系 | 区分已确认超配、资料未知与兼项；没有任务级所需工时不能推算具体任务延期天数 |
| 休假 / 非全勤 | 未来休假、状态与时间、交接人、任务计划窗口 | 已确认休假与计划重叠提示交接和调整；提议休假标待确认。填了交接人不等于交接已落实 |
| 接口 | 接口清单的关联任务、当前状态、预计就绪、接口负责人、说明链接 | 尚未就绪进入风险；关联任务可能是接口开发本身，未注明使用时点就不能认定必须在任务开始前完成 |
| 决策 | 提醒与风险中的待决定项，相关任务/任务反向关联、决定人、最迟时间、结论与依据 | 有效批准结论停止该决策请求；后续落实沿已有执行记录跟进；开放决定不自动等于整项目硬阻塞 |
| 物资及其他条件 | 提醒与风险中登记风险/问题/提醒，写清物资或条件、相关工作项、处理负责人、最迟时间、下一步、影响和来源 | 按登记事实进入风险材料；不凭标题关键词猜阻塞，不另造资产库存台账 |

员工仅豁免例行人力资源确认；**员工已有容量、休假和参与事实同样参与任务风险评估**。项目/运维容量口径不变，已扣休假不重复扣，驻场/远程不代表产能。

每项风险至少展示：来源记录、未落实事项、责任人、最晚落实或核对时点、关联任务与上级路径、项目影响、建议下一步和待评估依据。没有关联任务的接口/决定/物资仍列为“待定位风险”，由 PM 补关联，不能丢掉，也不能任意摊到全项目每个任务。

如果来源只明确关联运维事项，材料单列“运维资源风险”，不算作项目待定位风险，也不计入项目资源风险或叶子影响读数。只有运维事项明确连接项目 WBS 时，才沿该关系评估项目交付影响。

预计接口就绪日不是已确认的最晚使用日；休假开始、周容量窗口等日期仅作为来源事实，不冒充最晚落实或补填期限，承诺时点未知则注明待确认。未来已安排但尚未落实的资源可列潜在风险，不能因此自动标为已延期。已关闭/撤销事项停止本项风险提醒，历史事实仍留档。

报告只评估已登记的资源需求和关联。未登记的任务工时、替补确认、使用时点、到货依据属于待补信息，不能从“未发现问题”得出“所有资源已到位”。

## 复盘时怎么用

先看全项目完成与未就绪读数，再查看父级缺口，展开最小子任务路径。对资源风险逐项审议：谁落实、何时落实、采用什么措施、需要谁作决定。实际延期仍在“延期与补救审议”独立展示；措施建议、实际决定、落实结果分开记录。会后按 [会议行动契约](../references/meeting-actions.md) 回填，保留会前/会后材料。
